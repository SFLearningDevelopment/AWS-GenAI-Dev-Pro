Orientation

The scenario is an internal assistant over company policy documents — leave, travel, expenses, security. Questions must be answered from the documents, answers must carry citations, and an employee in one department must not be able to retrieve another department's confidential files.

Retrieval-augmented generation has two halves that fail differently. The ingestion half — parse, chunk, embed, index — decides what is findable. The query half — search, filter, rank, generate — decides what is used. When answers are wrong, the first diagnostic question is always which half broke, and stage 7 gives you a way to tell.

Glossary

Chunk
The unit that gets embedded and retrieved. Too small and an answer spans several chunks that never come back together; too large and the embedding blurs across topics so nothing matches sharply.
Embedding model
Turns text into a vector. The same model must be used at ingestion and at query time. Changing it means rebuilding the whole index.
Vector store
The searchable index. Bedrock knowledge bases support several backends; this lab uses OpenSearch Serverless, which is the default in the console wizard and the most likely one to appear in exam scenarios.
Data access policy
An OpenSearch Serverless authorisation document, separate from IAM, that names which principals may read or write which collections and indexes. Both systems must allow an action for it to succeed.
RetrieveAndGenerate
One API call that searches the knowledge base and passes the results to a model with a built-in prompt template. Retrieve is the same search without the generation step — the debugging tool.
Verify before you start

Embedding models, vector-store backends and console wizard steps in ap-south-1 move quickly. Confirm the available embedding models on the knowledge base creation screen and use what you find. Written against the console as of September 2026.

1

Lay out the corpus and its metadata

Console plus CloudShell. Structure decided here determines whether filtering is possible later.

Create a bucket, for example policy-corpus-<account>-aps1, in ap-south-1. Inside, use one prefix per department:

s3://policy-corpus-.../hr/leave-policy.pdf
s3://policy-corpus-.../hr/leave-policy.pdf.metadata.json
s3://policy-corpus-.../finance/expense-policy.pdf
s3://policy-corpus-.../finance/expense-policy.pdf.metadata.json
s3://policy-corpus-.../security/access-control.pdf

Each sidecar file carries attributes you can filter on at query time:

leave-policy.pdf.metadata.json

{
  "metadataAttributes": {
    "department": "hr",
    "classification": "internal",
    "effective_year": 2026,
    "doc_type": "policy"
  }
}

Use six to ten documents of real length. Two-paragraph test files make every retrieval look perfect and teach you nothing about chunking. If you have no corpus handy, export a few public AWS documentation pages to PDF and treat them as policies.

Exam lens

Metadata is the mechanism behind most multi-tenant and access-control answers in Domain 1. When a scenario says different user groups must see different subsets of one knowledge base, the reference design is a metadata attribute written at ingestion plus a filter applied at query time from the caller's verified identity — not separate knowledge bases per group, unless the isolation requirement is a hard compliance boundary.

Choose the vector store with your eyes open

Reading and one decision. Skipping this is how a lab account ends up with a surprise bill.

The knowledge base wizard offers to create a vector store for you. Before accepting, understand what you are agreeing to.

BackendShape of the costReach for it when
OpenSearch ServerlessBilled per OpenSearch Compute Unit-hour with a minimum allocation, whether or not you query itProduction RAG at scale; also the default the console suggests
S3 vector storageStorage plus per-request, no always-on floorLow query volume, cost-sensitive workloads, labs
Aurora PostgreSQL with pgvectorDatabase instance or ACU costVectors must sit beside relational data you already run
Third-party (Pinecone, MongoDB Atlas, Redis)Vendor pricing; credentials held in Secrets ManagerAn existing investment in that store
Cost

An idle OpenSearch Serverless collection keeps billing. If you pick it, put a calendar reminder to delete it, and delete it the same day you finish the lab. If your account is personal or the budget is tight, choose the S3 vector option and read the OpenSearch stages for the IAM content, which is what the exam tests.

If you go with OpenSearch Serverless, three policies exist around the collection, and they are frequently confused:

  • Encryption policy — which KMS key protects the collection. Required at creation.
  • Network policy — public endpoint or VPC endpoint access.
  • Data access policy — which principals may perform which collection and index operations. This is not IAM, and an IAM allow without a matching data access rule still fails.
Exam lens

"The role has aoss:APIAccessAll but ingestion fails with a permissions error" is a set-piece question. The answer is the missing data access policy entry for that role. Hold the reverse case too: a data access rule without the IAM permission fails just as surely.

3

Create the knowledge base and choose a chunking strategy

Console. The wizard makes several consequential choices on your behalf; make them deliberately.

  1. Bedrock → Knowledge Bases → Create, name it policy-kb, and let the console create a new service role.
  2. Data source: S3, pointing at your bucket. Leave the prefix empty so all departments are indexed into one knowledge base — filtering will handle separation.
  3. Choose an embedding model. Titan Text Embeddings v2 lets you select dimensions; 1024 is the accuracy-oriented default, smaller values cut storage and latency at some cost to recall.
  4. Choose a chunking strategy — see below.
  5. Create, then run the first Sync and watch the ingestion job to completion.
StrategyWhat it doesFits
DefaultFixed windows of roughly 300 tokens with overlapA reasonable first attempt at almost anything
Fixed sizeYou set token count and overlapUniform documents where you have measured a good size
HierarchicalSmall child chunks are searched, larger parent chunks are returnedLong structured documents — precise matching, wide context
SemanticSplits at meaning boundaries rather than token countsNarrative text where topics change mid-page
NoneOne chunk per fileYou have already chunked upstream, or files are tiny

Pick hierarchical for policy PDFs and note your choice. In stage 7 you will change it and observe the difference, which is more instructive than any table.

Verify

Chunking cannot be edited on an existing data source in place — changing it means recreating the data source and re-syncing. Confirm current behaviour in the console before you plan a migration around it.

Exam lens

Symptom-to-strategy mapping is the testable skill. Answers that quote the right sentence but miss the surrounding context suggest chunks that are too small or lack overlap. Answers that wander off-topic suggest chunks that are too large. A requirement for precise retrieval with wide context in one system points at hierarchical chunking.

4

Read the service role the console wrote for you

Console plus JSON. The highest-value fifteen minutes in this lab.

Open IAM → Roles and find the knowledge base service role. Read the trust policy first:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "bedrock.amazonaws.com"},
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {"aws:SourceAccount": "<ACCOUNT_ID>"},
      "ArnLike": {
        "aws:SourceArn": "arn:aws:bedrock:ap-south-1:<ACCOUNT_ID>:knowledge-base/*"
      }
    }
  }]
}

Those two conditions are confused-deputy protection. Without them, the Bedrock service principal could be induced by another customer's knowledge base to assume your role and read your bucket. This exact pattern reappears in Lab 3 on the agent role and on Lambda resource policies — learn it once here.

Now the permissions policy. It has three distinct jobs:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EmbedChunks",
      "Effect": "Allow",
      "Action": "bedrock:InvokeModel",
      "Resource": "arn:aws:bedrock:ap-south-1::foundation-model/amazon.titan-embed-text-v2:0"
    },
    {
      "Sid": "ReadCorpus",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::policy-corpus-<account>-aps1",
        "arn:aws:s3:::policy-corpus-<account>-aps1/*"
      ],
      "Condition": {
        "StringEquals": {"aws:ResourceAccount": "<ACCOUNT_ID>"}
      }
    },
    {
      "Sid": "WriteVectors",
      "Effect": "Allow",
      "Action": "aoss:APIAccessAll",
      "Resource": "arn:aws:aoss:ap-south-1:<ACCOUNT_ID>:collection/<COLLECTION_ID>"
    }
  ]
}

Then open OpenSearch Serverless → Data access policies and find the rule granting this same role aoss:*Document and index permissions on the collection. Two authorisation systems, one operation. Delete the data access rule, re-sync, watch it fail, restore it. That failure is worth more than reading about it.

Exam lens

Recognise aws:SourceArn and aws:SourceAccount on a service-principal trust policy as confused-deputy prevention, and aws:ResourceAccount on an S3 statement as a guard against reading buckets outside your account. Both show up as distractor-heavy multiple-response questions in Domain 3.

5

Query it from code, retrieval first

Code. Look at what comes back before you let a model write over it.

Start with retrieve alone. No generation means nothing can paper over a bad search.

import boto3, json

KB_ID = "<KNOWLEDGE_BASE_ID>"
agent_rt = boto3.client("bedrock-agent-runtime", region_name="ap-south-1")

def search(question, department=None, k=5):
    cfg = {"vectorSearchConfiguration": {
        "numberOfResults": k,
        "overrideSearchType": "HYBRID",
    }}
    if department:
        cfg["vectorSearchConfiguration"]["filter"] = {
            "equals": {"key": "department", "value": department}
        }

    r = agent_rt.retrieve(
        knowledgeBaseId=KB_ID,
        retrievalQuery={"text": question},
        retrievalConfiguration=cfg,
    )
    for item in r["retrievalResults"]:
        print(round(item["score"], 4),
              item["location"]["s3Location"]["uri"],
              item["content"]["text"][:140].replace("\n", " "))

search("How many days of paid leave carry over to the next year?")

Read the scores and sources. If the right document is not in the top five, generation cannot save the answer, and the fix is in ingestion — chunking, or the query wording, or a missing document.

HYBRID combines vector similarity with keyword matching. It usually wins when queries contain identifiers, product names or policy numbers that semantic search alone smooths over. Try both and compare on a query containing a specific term.

Now the full path:

MODEL_ARN = ("arn:aws:bedrock:ap-south-1:<ACCOUNT_ID>"
             ":inference-profile/apac.amazon.nova-lite-v1:0")

def answer(question, department=None):
    vsc = {"numberOfResults": 5, "overrideSearchType": "HYBRID"}
    if department:
        vsc["filter"] = {"equals": {"key": "department", "value": department}}

    r = agent_rt.retrieve_and_generate(
        input={"text": question},
        retrieveAndGenerateConfiguration={
            "type": "KNOWLEDGE_BASE",
            "knowledgeBaseConfiguration": {
                "knowledgeBaseId": KB_ID,
                "modelArn": MODEL_ARN,
                "retrievalConfiguration": {"vectorSearchConfiguration": vsc},
            },
        },
    )
    sources = [
        ref["location"]["s3Location"]["uri"]
        for c in r["citations"]
        for ref in c["retrievedReferences"]
    ]
    return r["output"]["text"], sorted(set(sources))

text, sources = answer("What is the carry-over limit on paid leave?", "hr")
print(text)
print(json.dumps(sources, indent=2))
Exam lens

Know when RetrieveAndGenerate is enough and when it is not. It is enough for a straightforward cited answer. It is not enough when you need to rerank results, merge sources from outside the knowledge base, or apply your own prompt structure — those call for Retrieve plus your own Converse call. Filters, top-k and search type are the three knobs worth memorising.

6

Put an authenticated endpoint in front

Console for wiring, code for the handler. The filter must come from identity, never from the request body.

Create a Lambda named policy-answer, Python 3.13, timeout 60 seconds, with a role granting bedrock:Retrieve and bedrock:RetrieveAndGenerate on the knowledge base ARN, plus bedrock:InvokeModel on the generation model and its inference profile.

import json, os, boto3

KB_ID     = os.environ["KB_ID"]
MODEL_ARN = os.environ["MODEL_ARN"]
agent_rt  = boto3.client("bedrock-agent-runtime")

def department_from_claims(event):
    """Derive the filter from the verified token, not from user input."""
    claims = (event.get("requestContext", {})
                   .get("authorizer", {})
                   .get("jwt", {})
                   .get("claims", {}))
    return claims.get("custom:department")

def lambda_handler(event, context):
    body = json.loads(event.get("body") or "{}")
    question = (body.get("question") or "").strip()
    if not question:
        return _resp(400, {"error": "question is required"})

    dept = department_from_claims(event)
    if not dept:
        return _resp(403, {"error": "no department claim on token"})

    vsc = {"numberOfResults": 5,
           "overrideSearchType": "HYBRID",
           "filter": {"equals": {"key": "department", "value": dept}}}

    r = agent_rt.retrieve_and_generate(
        input={"text": question},
        retrieveAndGenerateConfiguration={
            "type": "KNOWLEDGE_BASE",
            "knowledgeBaseConfiguration": {
                "knowledgeBaseId": KB_ID,
                "modelArn": MODEL_ARN,
                "retrievalConfiguration": {"vectorSearchConfiguration": vsc},
            },
        },
    )

    sources = sorted({ref["location"]["s3Location"]["uri"]
                      for c in r["citations"]
                      for ref in c["retrievedReferences"]})
    if not sources:
        return _resp(200, {"answer": "I could not find this in the policy documents.",
                           "sources": []})

    print(json.dumps({"event": "answered", "department": dept,
                      "source_count": len(sources)}))
    return _resp(200, {"answer": r["output"]["text"], "sources": sources})

def _resp(code, payload):
    return {"statusCode": code,
            "headers": {"content-type": "application/json"},
            "body": json.dumps(payload)}

Front it with an API Gateway HTTP API and a JWT authorizer backed by a Cognito user pool, with a custom attribute department on each user. Then try the attack: send {"question": "...", "department": "finance"} as an HR user. Because the handler ignores the body field entirely, nothing changes — which is the whole design.

The failure to avoid

Taking the filter value from the request body is the single most common tenant-isolation bug in RAG applications. It looks like it works in every test, because every test sends the right value.

Exam lens

Domain 2 scenarios on multi-tenant RAG have a consistent answer shape: authenticate at the edge, derive the filter server-side from verified claims, apply it in the retrieval configuration, and log the resolved tenant. Watch for distractors that filter after retrieval — by then the data has already left the store, and per-token cost has already been spent.

7

Measure retrieval, then tear down

Code. Turn "it feels better" into a number you can defend.

Write twenty questions whose correct source document you already know, then score retrieval alone:

eval_retrieval.py

import boto3

agent_rt = boto3.client("bedrock-agent-runtime", region_name="ap-south-1")
KB_ID = "<KNOWLEDGE_BASE_ID>"

CASES = [
    ("How many days of paid leave carry over?", "hr/leave-policy.pdf"),
    ("What is the per-diem limit for domestic travel?", "finance/expense-policy.pdf"),
    # ... 18 more
]

def hit_at_k(k=5, search_type="HYBRID"):
    hits = 0
    for question, expected in CASES:
        r = agent_rt.retrieve(
            knowledgeBaseId=KB_ID,
            retrievalQuery={"text": question},
            retrievalConfiguration={"vectorSearchConfiguration": {
                "numberOfResults": k, "overrideSearchType": search_type}},
        )
        uris = [x["location"]["s3Location"]["uri"] for x in r["retrievalResults"]]
        if any(expected in u for u in uris):
            hits += 1
    return hits / len(CASES)

for st in ("SEMANTIC", "HYBRID"):
    for k in (3, 5, 10):
        print(st, k, round(hit_at_k(k, st), 3))

Now change one variable at a time and re-measure: chunking strategy (recreate the data source), embedding dimensions, top-k, search type. Record the numbers. A retrieval score that does not move when you change the generation model is the clearest proof that your problem lives in ingestion.

For the generation half, Bedrock's built-in RAG evaluation jobs score answers on faithfulness to retrieved context, relevance and completeness using a judge model. Run one against your knowledge base and compare its verdict with your own reading of ten answers.

Exam lens

Domain 5 separates retrieval metrics from generation metrics, and expects you to diagnose in that order. An answer that is fluent, confident and wrong with correct citations attached is a grounding failure, addressed with a contextual grounding guardrail — which Lab 3 builds.

Tear down

  • Delete the vector store first if it is OpenSearch Serverless. This is the only resource here with a meaningful hourly cost.
  • Delete the knowledge base and its data source, the Lambda, the API and the Cognito user pool.
  • Keep the S3 corpus and the knowledge base ID noted if you plan to start Lab 3 soon — the agent lab attaches a knowledge base, and rebuilding takes twenty minutes.
  • Check Billing → Cost Explorer the next day and confirm OpenSearch charges have stopped.
