Invoke and govern a foundation model

Build a support-ticket triage function on Amazon Bedrock, then put the four things around it that a production reviewer will ask for: a scoped IAM role, a versioned prompt, invocation logs, and a guardrail.

Regionap-south-1 (Mumbai)
Time90–120 minutes
CostUnder ₹100 if you tear down
Exam domains1 and 3
You needAWS account with admin, basic Python
0 of 0 checks done

Orientation

You are building the triage step of a support pipeline. A ticket arrives, a Lambda function asks a foundation model to classify it (category, urgency, whether it contains customer data), and the structured result goes back to the pipeline.

The model call itself is about fifteen lines of code. Everything else in this lab is the part the exam actually tests: which identity is allowed to call which model, where the prompt lives and who can change it, what gets recorded, and what the model is forbidden to say.

Glossary

Converse API
Bedrock's model-agnostic chat interface. The same request shape works across providers, so switching models is a config change rather than a rewrite. Prefer it over InvokeModel unless you need a provider-specific field.
Inference profile
A routing target that stands in for a model. A system-defined (cross-region) profile such as apac.* spreads calls across several regions for throughput. An application inference profile wraps a model with your own cost-allocation tags. Both have their own ARN, and that ARN is what your IAM policy names.
Prompt Management
A Bedrock feature that stores prompts as versioned resources with variables. The prompt gets an ARN, so changing wording becomes a reviewable, auditable action instead of a code deploy.
Model invocation logging
An account-and-region-level Bedrock setting that writes request and response metadata (optionally full bodies) to CloudWatch Logs, S3, or both. Off by default.
Guardrail
A policy object evaluated independently of the model: denied topics, word and content filters, PII detection, and contextual grounding checks. It applies to both the input and the output.
Verify before you start

Model availability and inference-profile IDs in ap-south-1 change often. Every model ID in this lab is an example — confirm yours in stage 1 and use that value throughout. This lab was written against the Bedrock console as of September 2026.

1

Enable model access and find your real model ID

Console. Nothing works until the account has been granted access to a model in the region you are calling.

Bedrock access is per account, per region. An account with access in us-east-1 has none in ap-south-1.

  1. Sign in and set the region selector to Asia Pacific (Mumbai) ap-south-1.
  2. Open Amazon Bedrock → Model access.
  3. Enable at least one small, cheap text model — Amazon Nova Lite is a good default — and one Anthropic Claude model if your account is eligible. Serverless text models are usually granted immediately.
  4. Open Chat / Text playground, pick the model, and send one message. If this fails, stop here; nothing downstream will work.

Now get the identifier your code will use. Many models are not callable directly in ap-south-1 and must be reached through a cross-region inference profile whose ID starts with apac.:

aws bedrock list-inference-profiles \
  --region ap-south-1 \
  --query "inferenceProfileSummaries[].{id:inferenceProfileId,models:models[].modelArn}" \
  --output table

Pick one and keep both facts: the profile ID (for modelId) and the list of underlying model ARNs (for IAM in stage 3).

Exam lens

A call that works in one region and fails in another is a recurring question shape. Check three things, in this order. Model access is granted per account and per region, so it may simply not be enabled here. Some models cannot be called by bare model ID in a given region and must go through an inference profile, which surfaces as ValidationException. An IAM policy that names the model but not the profile ARN is denied even though the model is enabled, which surfaces as AccessDeniedException.

The error type narrows it for you: a validation error points at the request, an access denied points at the policy.

2

Make the call by hand before you make it in Lambda

Code. Get a working Converse call in CloudShell so that later failures are clearly IAM or packaging, not the request.

Open CloudShell in ap-south-1 and save this as triage.py.

triage.py

import json, boto3

MODEL_ID = "apac.amazon.nova-lite-v1:0"   # replace with your stage 1 value
brt = boto3.client("bedrock-runtime", region_name="ap-south-1")

SYSTEM = """You triage customer support tickets.
Reply with JSON only, no prose, matching exactly:
{"category": "billing|technical|account|other",
 "urgency": "low|medium|high",
 "contains_personal_data": true|false,
 "summary": "one sentence"}"""

def triage(ticket_text):
    resp = brt.converse(
        modelId=MODEL_ID,
        system=[{"text": SYSTEM}],
        messages=[{"role": "user", "content": [{"text": ticket_text}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0, "topP": 0.9},
    )
    text = resp["output"]["message"]["content"][0]["text"]
    return json.loads(text), resp["usage"], resp["stopReason"]

if __name__ == "__main__":
    body, usage, stop = triage(
        "Charged twice for the October invoice on card ending 4417. "
        "Reply to arun.k@example.com. This is blocking our month-end close."
    )
    print(json.dumps(body, indent=2))
    print(usage, stop)

Run python3 triage.py. Three fields in the response deserve attention:

FieldWhy it matters
usageInput and output token counts. This is your unit of cost and the thing you alarm on later.
stopReasonend_turn is clean. max_tokens means you truncated the model mid-JSON — the parse will fail, and raising maxTokens is the fix.
content[0]["text"]Content is a list of blocks. Indexing [0] is fine now but breaks the moment you add tool use or reasoning blocks.
Exam lens

Three controls shape sampling and they are not interchangeable. temperature flattens or sharpens the probability distribution over next tokens; topP truncates the candidate pool by cumulative probability; topK truncates it by count. In Converse, temperature, topP, maxTokens and stopSequences go in inferenceConfig, but topK does not — it goes in additionalModelRequestFields, and only for models that accept it. A question describing a ValidationException after adding topK is testing that placement, not tuning.

Scenario questions state a requirement and expect you to move in the right direction: consistent extraction of invoice fields or ticket labels means driving variance down, which is why this lab uses temperature: 0; varied marketing copy means the opposite. Watch for the distractor offering a parameter change as the fix for malformed output — if the model wraps its JSON in prose, no sampling setting corrects that, and the answer is a stricter prompt, a stop sequence, or tool use with a schema.

3

Write the execution role yourself

Console plus JSON. This is the stage the exam weights most heavily, so do not take the managed-policy shortcut.

Create an IAM role named triage-ticket-role with Lambda as the trusted entity, attach AWSLambdaBasicExecutionRole for CloudWatch Logs, then add an inline policy named bedrock-invoke-triage:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "InvokeThroughInferenceProfile",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:ap-south-1:<ACCOUNT_ID>:inference-profile/apac.amazon.nova-lite-v1:0",
        "arn:aws:bedrock:ap-south-1::foundation-model/amazon.nova-lite-v1:0",
        "arn:aws:bedrock:ap-northeast-1::foundation-model/amazon.nova-lite-v1:0",
        "arn:aws:bedrock:ap-southeast-1::foundation-model/amazon.nova-lite-v1:0"
      ]
    },
    {
      "Sid": "WriteTriageResults",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::<RESULTS_BUCKET>/triage/*"
    }
  ]
}

Two things to notice. Foundation model ARNs have an empty account field — the models are not yours. And when you call through a cross-region profile, the profile ARN alone is not enough: the request is authorised against the profile and the underlying model in whichever region it lands in. List every region the profile routes to, or you will get intermittent denials that look like a flaky service.

Do not do this

"Action": "bedrock:*" with "Resource": "*" will pass this lab and fail a security review. It grants the ability to create guardrails, delete prompts, and start expensive customisation jobs from a function whose only job is to classify text.

Now test the boundary. Add a second statement denying one model you did not intend to use, or temporarily remove one region ARN and rerun. Watching the call fail teaches you more than watching it succeed.

Exam lens

Bedrock authorises against the routing target, not the model family, and most questions in this area turn on that. A role allowed on a foundation model ARN but not on the inference profile it is actually called through is denied — and so is the reverse.

Two condition keys recur. aws:ResourceTag scopes a role to one team's tagged application inference profile, which is how per-team access is granted without listing models. aws:SourceVpce on the invoke statement forces traffic through a VPC endpoint, which is the answer whenever a scenario says model calls must not traverse the public internet.

Done when
4

Deploy the triage function

Console for creation, code for the handler.

Create an S3 bucket for results, then Lambda → Create function: name triage-ticket, runtime Python 3.13, existing role triage-ticket-role. Under Configuration → General set timeout to 60 seconds and memory to 512 MB — the default 3-second timeout is shorter than many model responses.

lambda_function.py

import json, os, uuid, boto3

MODEL_ID = os.environ["MODEL_ID"]
BUCKET   = os.environ["RESULTS_BUCKET"]

brt = boto3.client("bedrock-runtime")
s3  = boto3.client("s3")

SYSTEM = """You triage customer support tickets.
Reply with JSON only, no prose, matching exactly:
{"category": "billing|technical|account|other",
 "urgency": "low|medium|high",
 "contains_personal_data": true|false,
 "summary": "one sentence"}"""

def lambda_handler(event, context):
    ticket = event.get("ticket", "")
    if not ticket.strip():
        return {"statusCode": 400, "body": "ticket is required"}

    resp = brt.converse(
        modelId=MODEL_ID,
        system=[{"text": SYSTEM}],
        messages=[{"role": "user", "content": [{"text": ticket}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0},
    )

    raw = resp["output"]["message"]["content"][0]["text"]
    try:
        result = json.loads(raw)
    except json.JSONDecodeError:
        # Model drifted off format. Fail loud rather than guessing.
        print(json.dumps({"event": "parse_failure", "raw": raw[:500]}))
        return {"statusCode": 502, "body": "model returned unparseable output"}

    record = {
        "id": str(uuid.uuid4()),
        "request_id": context.aws_request_id,
        "model_id": MODEL_ID,
        "usage": resp["usage"],
        "result": result,
    }
    s3.put_object(
        Bucket=BUCKET,
        Key=f"triage/{record['id']}.json",
        Body=json.dumps(record).encode(),
        ContentType="application/json",
    )
    print(json.dumps({"event": "triaged", **record["usage"],
                      "urgency": result.get("urgency")}))
    return {"statusCode": 200, "body": json.dumps(record)}

Set environment variables MODEL_ID and RESULTS_BUCKET, deploy, and test with {"ticket": "..."}.

Verify

If converse is missing from the runtime's bundled boto3, the error is AttributeError, not a permissions error. Attach a recent AWS SDK for Python layer or bundle boto3 with the deployment package.

Exam lens

Two design points hide in this handler. Structured logging of token usage per request is what makes per-tenant cost attribution possible later. And failing on a parse error rather than retrying blindly matters — a retry loop against a model that keeps producing prose burns money and returns nothing.

Done when
5

Move the prompt out of the code

Console for authoring, code for invocation. The prompt becomes a versioned resource with its own ARN.

A prompt embedded in a handler can only be changed by someone who can deploy code, and its history lives in a git repo nobody audits. Prompt Management fixes both.

  1. Open Bedrock → Prompt management → Create prompt, name it ticket-triage.
  2. Paste the system text into the prompt body and add a variable placeholder {{ticket}} for the user content.
  3. Select your model and set temperature 0, max tokens 400.
  4. Test it in the builder, then choose Create version. Note the ARN and the version number.

Now call the prompt instead of the model. The prompt ARN goes where the model ID used to be:

resp = brt.converse(
    modelId="arn:aws:bedrock:ap-south-1:<ACCOUNT_ID>:prompt/<PROMPT_ID>:1",
    promptVariables={"ticket": {"text": ticket}},
)

Model choice and inference config now live in the prompt version, not in your code. Add these permissions to the execution role, scoped to the one prompt:

{
  "Effect": "Allow",
  "Action": ["bedrock:GetPrompt", "bedrock:RenderPrompt"],
  "Resource": "arn:aws:bedrock:ap-south-1:<ACCOUNT_ID>:prompt/<PROMPT_ID>"
}
Pin the version

Pointing at the bare prompt ARN with no :1 suffix resolves to the draft, which anyone with console access can edit. Production must reference an immutable version. Promotion is then a config change: point the function at :2, and roll back by pointing it at :1.

Exam lens

Domain 1 asks about prompt governance directly. The reference answer combines Prompt Management for versioned templates and approval flow, CloudTrail for who changed what, and CloudWatch Logs for access — plus a regression check (a Lambda that runs known inputs through a new version and compares outputs) before promotion.

Done when
6

Turn on invocation logging and a cost alarm

Console. Bedrock records nothing about model calls until you ask it to.

Your Lambda logs prove the function ran. They do not prove what was sent to the model, which is what an auditor asks for.

  1. Bedrock → Settings → Model invocation logging, enable it.
  2. Select both destinations: a CloudWatch log group /aws/bedrock/invocations and an S3 prefix. Console-created roles and bucket policy come with the setup; read them rather than clicking past.
  3. Choose which data types to log — text, image, embedding. Logging full request and response bodies is what makes the logs useful and also what makes them sensitive.
  4. Invoke the function, wait a minute, and read one log record end to end.

The S3 bucket policy the console generates is worth understanding. It allows the bedrock.amazonaws.com service principal to write, and constrains it with aws:SourceAccount and aws:SourceArn so another account cannot induce Bedrock to write into your bucket.

Then add one alarm. In CloudWatch, create an alarm on the Bedrock metric InputTokenCount (dimension by model), summed over one hour, with a threshold roughly three times your expected volume.

Data protection

Full-body logs now contain every ticket, including the card fragment and email address in the sample. Apply SSE-KMS on the bucket, a lifecycle rule to expire objects, and a restrictive log-group policy — or log metadata only. Deciding this consciously is the point of the stage.

Exam lens

Distinguish the three observability layers cleanly: CloudTrail records the control-plane action (who created the guardrail), model invocation logging records the data-plane payload (what was sent to the model), and CloudWatch metrics record volume and latency. Questions about "we need to know what a user asked the model six months ago" point at invocation logging plus S3 retention.

Done when
7

Attach a guardrail, then tear down

Console for the guardrail, one code change to enforce it.

Prompt instructions are a request. A guardrail is enforcement, evaluated separately from the model, so it still holds when someone injects instructions inside a ticket body.

  1. Bedrock → Guardrails → Create guardrail, name it triage-guardrail.
  2. Denied topics: add one — legal advice, say — with a short description and a couple of examples.
  3. Sensitive information: add EMAIL and CREDIT_DEBIT_CARD_NUMBER with action Mask. Masking on input means the model never sees the raw values.
  4. Content filters: leave at medium and note that prompt-attack detection applies to the input side.
  5. Test in the console with the sample ticket, then Create version.

Enforce it in the call:

resp = brt.converse(
    modelId=MODEL_ID,
    system=[{"text": SYSTEM}],
    messages=[{"role": "user", "content": [{"text": ticket}]}],
    inferenceConfig={"maxTokens": 400, "temperature": 0},
    guardrailConfig={
        "guardrailIdentifier": "<GUARDRAIL_ID>",
        "guardrailVersion": "1",
        "trace": "enabled",
    },
)

if resp["stopReason"] == "guardrail_intervened":
    print(json.dumps({"event": "blocked", "trace": resp.get("trace")}))
    return {"statusCode": 200, "body": json.dumps({"status": "blocked"})}

Add bedrock:ApplyGuardrail on the guardrail ARN to the execution role. Then send a ticket that asks for legal advice and confirm you get guardrail_intervened rather than an answer.

Exam lens

Two distinctions to hold. Guardrails are a separate resource with their own versions and can be shared across models and applications — the answer to "we need one policy across three teams' apps" is one guardrail, not three prompts. And ApplyGuardrail can be called standalone to screen text that never goes to a model at all, such as user-generated content.

Tear down

  • Delete the Lambda function, the IAM role, and the S3 results bucket.
  • Disable model invocation logging and empty or delete the log bucket and log group.
  • Delete the guardrail and the prompt, or keep them — neither costs anything at rest.
  • Delete the CloudWatch alarm.
